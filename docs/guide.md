## Workspaces, accounts and switching

Open the composer’s agent/model button to browse cloud agents and downloaded Ollama models in one searchable panel. Selecting a model prepares the next prompt; only Send starts inference. Local selections stay with their workspace, preserve cloud preferences, and support text/code attachments. Images require a cloud connection and are never silently discarded. The legacy model/agent controls remain available as a fallback if the picker script cannot load.

Click **New workspace** or **Add workspace**, name the project, and select its folders. For example, a Shop workspace can contain its admin panel, backend and website together. Its single chat opens automatically; there is no New chat button or conversation list. Use **Workspace settings › Add folder** to attach more folders: type one path per line, or use **Choose folders…** and hold ⌘ to select several at once in the Mac's folder picker. They are added together, and if one of them can't be opened, none is. The remove control next to a folder detaches it. Files remain on disk, and folder changes preserve the same chat and drafts. The final folder cannot be removed.

The sidebar switches between workspaces and displays their attached folders. Codex and Claude receive every current folder when you explicitly run them. Gemini on the Antigravity connection also receives the primary folder and all additional attached folders when its runtime reports support, keeping the work in the same workspace chat. This capability is available in the bundled Antigravity 1.4.5 runtime. A runtime that reports no additional-folder support asks which folder to use and starts the message as a task there. Flow routing and automatic handoff use the same reported capability. The advanced Gemini CLI connection supports a primary folder plus up to five additional folders. Adding/removing folders reconstructs provider sessions with the current access scope while retaining application history. Folder changes are blocked during active runs or file mutations. Missing folders stay listed with the saved chat available; remove or restore them before starting another run.

Existing projects migrate without changing IDs or deleting journals. The most recently updated legacy chat becomes the permanent chat; additional old chats remain saved as read-only archives. The previous registry is backed up as `projects.json.v1-backup`. Existing independent projects are not automatically combined; attach the relevant folders to the workspace you want to use.

**Settings** has its own dialog, opened from the status bar or **Settings…** in the desktop menu (⌘, on macOS). Its sidebar has four pages, and **Search settings** finds matching controls across all of them:

- **General:** appearance, Keep awake, when to offer or automatically make a handoff near usage limits, and updates. These apply across workspaces; the agent, model, access and routing for the current conversation stay in the composer and Agents panel.
- **Accounts:** connect agents, check their account status and usage, and explicitly allow API or unconfirmed billing for this app session.
- **Alerts:** banners, sounds, the Dock or taskbar, menu bar status, and the recap shown when you return.
- **Voice:** voice input, sending after speaking, and reading summaries aloud.

**Ask a friend** opens separately, with its own request and returned-solution pages. Folder management and remembered approvals stay in **Workspace settings**.

Open **Settings › Accounts** to inspect authentication, billing and usage. Choose the model and effort in the composer. Installed and authenticated are different states. Background checks keep the last result on screen; Settings shows when each connection was last checked, says when a newer check timed out or failed, and **Refresh status** checks again. Connect uses the provider's own supported authentication flow. Claude runs the official unmodified installed Claude Code binary; login happens through Claude Code. For personal Google accounts, choose **Install Google connection** in Settings or onboarding, then **Connect account**. Codeshi downloads the official [Antigravity ACP server](https://github.com/agentclientprotocol/registry/tree/main/antigravity-acp), verifies its pinned SHA-256 checksum, and starts Google's personal OAuth flow. The runtime manages its own authentication in an isolated application profile; Codeshi never extracts credentials. Models and thinking levels come from that account's native session metadata. Google's account eligibility and usage limits apply; no unlimited free usage is promised. Google [moved consumer Gemini CLI access to Antigravity on June 18, 2026](https://developers.google.com/gemini-code-assist/docs/deprecations/code-assist-individuals). Gemini CLI 0.66.0+ remains an advanced API-key/enterprise option via `AI_RELAY_GEMINI_BIN`. Plain `agy -p` headless mode is not used. Existing native login methods remain available. Codeshi does not extract tokens or copy another application's credential store.

Subscription, API and unknown billing are shown separately. Unknown or separately billed modes require explicit acceptance before an explicit provider run. There is no automatic API fallback. Usage stays unknown when the provider cannot report it. A model can be selected from current provider metadata or entered explicitly; selected models persist separately for each provider. Effective models are recorded when reported.

Use any connected assistant in the project’s existing chat. Wait or press **Stop** before switching. Consecutive messages to the same Claude or Codex agent resume its current native session and supply unseen shared context. Switching agents, including returning from a local run, starts a fresh session rebuilt from the shared journal rather than resuming that agent's older thread; Gemini continues its own session too, when its runtime can resume one. **Continue with…** explicitly reconstructs a fresh session from saved application history after an interruption or an unusable native session. Switching the selector alone makes no model request. Only **Send** or **Continue** starts inference.

The application history is canonical. Native Claude, Codex and Gemini sessions remain separate. Hidden reasoning, native tool execution state and unfinished OS processes are not transferred. Full history stays saved. Within each run’s byte budget, saved summary, goal, decisions and tasks stay intact; the original user request and eight latest substantive user instructions take priority over assistant progress and tool logs. Oversized historical messages become explicit excerpts, and command output has a separate small allocation. The run details show fresh versus resumed sessions, included and omitted message counts, and compacted logs. If essential context cannot fit, sending fails before starting the agent; shorten the current request, attachments or saved context. Summaries are not automatically generated with AI. Errors distinguish quota, authentication, installation, permission, interruption and protocol failures.

Automatic context refresh is on by default. When the context signal reaches the selected target, Codeshi starts a fresh native session on the next send with a bounded task brief while keeping the same workspace chat and its saved history. Older Claude and Codex sessions without a usable context reading refresh once on their next send after upgrading. Provider readings guide subsequent refreshes; recorded activity supplies a labeled estimate when readings are unavailable. Choose **Settings → While agents work → Context limit** to adjust Normal mode; Flow uses its routing mode's target. The **Compact context** icon at the top-right of the typing box opens the agent’s context details. It stays icon-only at every width: quiet during normal use, a small dot near the target, a check when the next refresh is arranged, and a gentle animation while context is being organized. Reduced-motion preferences disable the animation. The tooltip and accessible name explain each state. Context readings and progress toward the refresh target appear inside the panel, with estimates and unavailable readings labeled. You can inspect it during a run; manual refresh is available when agents are idle. Confirming **Refresh on next send** schedules the refresh locally without running a model summary. The next message to that agent builds a bounded task brief and starts a fresh session. Scheduled or automatic refreshes need no repeat confirmation. Flow may route a message to another agent; the scheduled refresh waits for its own agent. Your draft and full chat stay saved, while older details may leave the active context. The icon is hidden before an agent has a session and for agents that already start fresh each turn. `/compact` opens the same details.

Codex normally uses its official app-server with GUI approval requests. Claude uses the official Agent SDK with its installed binary and GUI `canUseTool` approvals. The advanced Gemini CLI connection uses ACP (`--acp`) with an isolated per-run policy that disables extensions, hooks, MCP, skills, telemetry and auto-memory, restricts read-only runs to read/search tools, routes edits and shell commands through one-time approvals, proxies text files within attached folders, and refuses managed system configurations it cannot safely combine. Antigravity uses its official ACP runtime in the confirmed `default` approval mode, routing one-time permissions to Codeshi. Interactive questions and workspace-trust requests are never automatically answered. Native workspace hooks and trust remain under Antigravity’s control. Its connection does not claim a read-only sandbox: choose Codex or Claude for read-only work and background reviews. No unrestricted execution flag is enabled. Read-only uses the provider's sandbox/restricted tools; Claude and Gemini restrictions are not an operating-system sandbox. User/project hooks are disabled for managed runs where supported; administrator provider policy can still apply. These controls do not isolate unrelated host processes.

Auto uses a higher refresh target after recent provider requests to preserve reusable context: 120,000 tokens in Normal and Balanced, 80,000 in Saving, and 160,000 in Quality. After a longer pause the targets are 75,000, 40,000 and 120,000 respectively. Targets are capped at 75% of a reported model window. Cache timing follows provider reports where available, with a conservative five-minute fallback; it does not guarantee a cache hit. Changing model or effort removes this allowance, and custom Normal limits stay fixed. Native agents manage compaction during a run. The memory brief keeps sourced user decisions and question answers, recent task outcomes and unfinished steps; command inputs and successful diagnostics do not become blockers.

After every prompt, Normal and Flow check locally whether that run used a lot, with no model call. A notice appears above the message box in two cases:

- **The run was well above your usual.** It has to reach at least three times the agent's median and sit above nearly all of its last 30 runs. Until an agent has eight runs to compare, only a run of 20 million tokens or more counts. After a notice, that agent's next four runs get another for their size only if they are at least twice as large.
- **A plan limit moved a lot while it ran.** That means 15 points of a limit such as the 5-hour one, 3 points of a weekly one, or crossing 80%. Codeshi reads the limit on each side of a run, which costs no allowance and holds nothing up. Limits count all use of the account, so another app or task can add to a move. One limit filling up is mentioned once per reset period, then again only if it moves at least twice as far or crosses 80%. Accounts billed by API report no plan limits.

The notice offers at most one action. **Compact** appears when the agent's context is 40,000 tokens or more and not yet due for a refresh, including when automatic refresh is off. If a refresh is already due or scheduled, the notice says so and asks for nothing. In Flow, when Compact doesn't apply, **Use Cost saving** switches the routing mode, unless it is already on. Dismissing a notice applies to that run. The run details keep each run's total, what is usual for that agent and how each limit moved, whether or not a notice appeared. A long run can still grow its own context well past the target, because a refresh only happens between turns.

### Permission controls and tool approvals

Codeshi provides two distinct permission choices in the composer toolbar:
- **Ask before changes** (the default): Actions that only read your workspace folders go ahead without asking: reading and searching files, listing folders, and read-only commands such as `ls`, `cat`, `rg`, `git status`, `git diff` and `git log`. Everything else appears in the app for approval before it runs: editing, creating or deleting files, installing packages, running project scripts or tests, network access, and any read outside the workspace folders. Commands Codeshi cannot fully judge, such as ones that chain commands, redirect output, substitute values or use variables, always ask.
  When an approval names one exact action, **Approve** has a menu for allowing that same action again without asking: **Allow for this run** lasts until the run ends, and **Always allow in this workspace** is remembered for the workspace. A remembered command covers only that agent, those exact words and that folder (single commands only, never chained, piped or redirected); a remembered edit covers only that file. Anything else can only be allowed once. The activity log names the rule that allowed an action. Review and revoke remembered approvals in **Workspace settings › Remembered approvals**; they never carry over to other workspaces or imported conversations.
- **Full auto-approval**: Agents' permission requests are approved automatically for that workspace, without a click. Claude and Gemini ask for each tool, and those steps show in the run as usual. Codex keeps its sandbox with the network on, so pushes and package installs just work, and asks only for what the sandbox still blocks, such as writing outside the workspace folders; each of those shows as an **Auto-approved** step. The selected access mode still applies: in **Read only**, Codex can't ask, and the run says when that setting blocked something.

Claude runs that start background commands keep their permission connection open for the follow-up work those commands trigger, including a slow follow-up request. **Stop** still cancels the run while it waits. A command that never reports back ends the wait with an explanation rather than keeping the run open indefinitely.

**Questions from an agent.** Claude can stop to ask you to choose, such as which library to use or where to store something, and Codex can where its connection asks. The question waits where approvals do, as a card with the choices, the one the agent suggests marked **Recommended**, and **Something else…** for your own answer when the agent allows it. Several questions show one at a time, with their headers as tabs. Choose with a click or a number key: a single choice moves on to the next question, **Next** does the same, and **Submit** sends your answers once each question has one. **Skip** lets the agent decide on its own. While it waits, the run status, the menu bar, alerts and the approval sound say an agent is waiting for your answer; full auto-approval never answers for you. Asking changes nothing, so agents can ask in read-only workspaces too, and a background review never asks. Your answers are saved in the conversation, so the next agent knows what you decided; an answer Codex asks to keep hidden is not written down.

Permission policies are strictly scoped to the workspace:
- New workspaces always start with **Ask before changes** (`approvalPolicy: 'ask'`).
- Importing a conversation (via native transcript discovery or shared file import) never imports or alters permission settings.
- Reopening a saved workspace remembers its configured policy.
- Changing the permission policy in the composer affects subsequent runs; in-flight runs and existing pending approvals retain their original policy.
- Incompatible configurations are strictly rejected: a run cannot be marked read-only if writes are permitted, and combining **Read only** with **Full auto-approval** is blocked with an explicit error explaining that read-only access blocks edits while auto-approval requires edit mode.

Automatic executable discovery checks absolute PATH entries, common install folders (including Homebrew, Volta, nvm, pnpm, Bun, mise, asdf and fnm), macOS app bundles and compatible Codex VS Code extensions. On Windows, a CLI installed with npm or pnpm is a `.cmd` script, which Codeshi never starts through a shell: it starts the native program the script points to (Claude Code's `claude.exe`, or the Codex build that Codex's launcher would start). Overrides are explicit and do not silently fall back:

```sh
AI_RELAY_CODEX_BIN=/absolute/path/to/codex AI_RELAY_CLAUDE_BIN=/absolute/path/to/claude AI_RELAY_GEMINI_BIN=/absolute/path/to/agy_acp_server.par npm start
```

## Local models

**Local** in the workspace header, **Continue locally** after an interrupted run, or **Agent › Continue Locally…** opens a handoff to a downloaded Ollama model. Use it when a cloud allowance runs out or when you prefer local inference. Select the model, review the task and current access mode, then press **Continue locally**. Opening the panel only reads model metadata; it never downloads a model or starts inference.

Setup:

1. Install [Codex CLI](https://github.com/openai/codex) for workspace tools and native approvals, and [Ollama](https://ollama.com/download) for model inference. This connection does not require a ChatGPT or Claude subscription or sign-in.
2. Download a coding model that supports tools using Ollama. Model capability, speed and memory needs vary; choose one that fits your hardware. Follow [Ollama's Codex setup](https://docs.ollama.com/integrations/codex), including a context window of at least 64K for longer coding tasks. Codeshi does not start or reconfigure the Ollama server for you.
3. Start Ollama, open a workspace in Codeshi, choose **Local**, and refresh the model list. Only verified downloaded GGUF models with tool support appear. Cloud models and aliases reporting a remote backend are excluded.

The default address is `http://127.0.0.1:11434`. For another local port, set `AI_RELAY_OLLAMA_URL` before starting Codeshi. Only HTTP loopback addresses are accepted; redirects and credentials in the address are rejected. No remote model endpoint can be selected from this panel.

The handoff includes the current folders, saved project brief, task and recent conversation within a 96 KB prompt budget. The first version is text-only: historical images are explicitly omitted, while their original snapshots and the full conversation stay saved. The model should inspect current files before repeating unfinished actions. Hidden reasoning, native tool state and running processes are not transferred.

Local inference uses Ollama through Codex's tool harness, with the workspace's current read/edit mode and existing approval controls. A model's identity is checked again before starting; changed or removed models require refreshing the selection. A provider mismatch stops before any task is sent. Local runs never switch to a cloud model or consume a connected cloud plan allowance. They use your computer's resources and depend on the configured model and Ollama context window.

Cloud selections and native sessions stay saved. Each local handoff starts a fresh ephemeral tool session, and its messages, results, activity and local-model attribution remain in Codeshi's permanent project conversation. **Stop** cancels the run. Continue with a cloud agent later through the normal composer; it receives the shared local work as context. The original composer draft is preserved when you start a local task. Conversation exports retain local-model attribution.

## Remote access away from home

Choose **Remote access → Connection → Away from home → Enable remote access**. Scan the QR, which opens `remote.codeshi.dev`, compare the six-digit number on both screens, then choose **Allow** on the computer. The phone uses the same minimal interface over mobile data or another Wi-Fi network; no account, mobile app or certificate installation is needed on the phone.

The computer must stay awake and online with Codeshi running. Prompt text, replies and approval details are encrypted on the devices before passing through Firebase. Remote control uses the existing access, billing, task and approval checks, and a phone cannot change its own grant. **Remove device** revokes access; restarting Codeshi turns it off. Access lasts up to 12 hours and new browsers always require approval. The phone closes its live connection while hidden and reconnects on return; lock-screen notifications are not included.

Remote access runs on a free service with a limit on simultaneous connections, shared by everyone using it. If it's busy or unavailable, the phone and **Remote access** say so and keep retrying, and a same-Wi-Fi connection still works.

Same-Wi-Fi pairing has its own on/off control and continues working without Firebase or internet access. The remote pilot shares Firebase Spark quotas across all users, and large photos or responses may exceed its 1 MiB packet limit. Maintainer setup, retention details and local tests are in [remote/README.md](../remote/README.md).

## Remote access on the same network

Any Codeshi user can connect a phone or tablet browser to their running computer; no mobile app or Apple Developer account is needed. Both devices need to be on the same private Wi-Fi or local network, and the computer must stay awake with Codeshi open.

1. On the computer, click **Remote access** in the bottom bar, or open **Settings › General › Remote access**, and choose **Enable same-Wi-Fi access**. If several network addresses are available, choose the one on your phone's network first.
2. Scan the QR code with your phone camera and open the link. The QR is generated locally and works once, for five minutes. **Can’t scan? Use a code or link** offers the address, an eight-digit code and a link you can copy instead. **New QR code** replaces the previous code and link.
3. The phone shows a six-digit number. Check that the computer shows the same one, then choose **Allow** in the computer's Remote access settings. The phone opens by itself. If you typed the address and code instead of scanning, name the browser and choose **Connect** first.

The phone has its own page, made for one hand, on the same saved workspaces and conversations as the computer. Work and agent sign-ins stay on the computer.

- **The conversation** fills the screen, with what the agent is doing now and how long it's been going just above the message box. A line separates each message an agent writes, so the latest is easy to find. The full list of its actions stays on the computer, which keeps the phone's data use low. The latest 40 messages load first; **Show earlier messages** brings more.
- **The message box** stays right above the keyboard. **+** attaches a photo, shrunk first to fit the attachment limit. The microphone beside Send turns your speech into text as you speak, using the phone's own browser: on an iPhone or Android phone that sends the audio to Apple or Google, unlike the computer, where speech never leaves your Mac. The first use says so, and nothing is sent until you press Send, which also turns the microphone off. Typing or moving to another conversation turns it off too, keeping the words as a draft. Browsers only allow the microphone on a secure connection, so on Same Wi-Fi the button is dimmed and a tap explains this; pair with **Away from home** for voice, which works on Wi-Fi too. The keyboard's dictation key works on both. While a run is working, Send adds your message to the queue, and **Add to this run** gives it to the agent now. **Up next** lists what's queued, to reorder, remove or resume. The phone can't start the computer's microphone.
- **What needs you** appears above the message box, one thing at a time: an approval with the exact command, a question with its choices, a handoff or a retry. Buttons on a new request wait half a second, so a tap meant for Send can't approve it. Answering on one device doesn't make it run again on the other. A request elsewhere shows as a line at the top that takes you there.
- **The name at the top** opens your workspaces, with the Workspace chat and tasks of the open one, and **New task**. **Appearance** (System, Light or Dark) and **Disconnect this phone** are at the bottom of that list. The phone's appearance is its own, so it doesn't change the computer's.
- **The line under the message box** shows the agent, model and access, and opens **How it runs**: agent with its usage, access, model and effort. Opening it puts the keyboard away. Settings lock while a run is working. If an agent isn't billed to a subscription, you're asked before each message. Routing shows here only while it's on, to change or turn off.
- **Stop** takes two taps, since it sits right above Send.

Reviewing and merging a task, files, Git, the terminal and Settings stay on the computer. A sound plays when an agent needs you or finishes only while the page is open, and only after a first tap on the page, which is the browser's rule.

The computer's bottom-bar phone button shows when access is on or a phone is connected, and a count when a new browser is waiting for your approval.

Pairing grants control of all saved workspaces, so only approve your own trusted browser. The connection uses **unencrypted HTTP** and is intended for trusted home or office networks. A pairing code works once and expires after five minutes; pending requests also expire after five minutes. An approved browser stays connected for up to 12 hours. **Remove device** revokes its connection; **Turn off** disconnects every phone. Access is off after quitting or restarting Codeshi, and devices must pair again.

If the phone cannot connect, allow Codeshi's local-network/firewall prompt, check that both devices use the same network, and avoid guest Wi-Fi that isolates devices. If the computer's address changes, turn access off and enable it again. **Keep awake** in General settings can help while an agent works. Progress resumes when the browser returns to the foreground; lock-screen notifications, iPhone Live Activities and access away from the local network are not included.

## Models, runs, Git and usage

**Layout.** The sidebar holds your workspaces and their files. The conversation is in the middle, with a panel under it for the **Terminal** and **Run**, with a side panel on the right that has five tabs: **Agents** (plan usage, **Routing** and **Handoff**), **Brief** (what every agent is told: memory and skills), **Tasks** (what each task used, and its limits) **Git**, and **Timeline** (checkpoints and workspace restore): the icon tabs at its top switch between them. Two layout buttons at the right of the search bar show or hide the sidebar (⌘B) and the side panel; each is filled while its area shows, and ⌘J shows or hides the bottom panel. **Terminal** and **Run** are also always at the left of the status bar, open or not: click one to open it, and click it again to hide the panel. With the sidebar hidden, the top bar names the open workspace; click the name to show the sidebar again. The side panel opens on the tab you last used, **Agents** on first launch. The top bar is a search bar (⌘K) for workspaces, files in every workspace (private paths such as `.git`, `node_modules` and `.env`, and build output, are never listed) and actions, including tools that open a window: **Review changes**, **Ask a friend**, **Previous chats** and **Export conversation**. They are also in the desktop **File** menu, and Review and Ask a friend appear under a finished run when there are changes. Drag the edge of the sidebar or the side panel, the line between workspaces and files, or the top of the bottom panel to resize them; the handles also move with the arrow keys, double-clicking one resets it, and sizes are remembered.

**Flow** (#107). The **Flow** button at the right of the header (⌘⇧F, or **View › Flow Mode**) keeps just the chat, in the middle, and puts away the sidebar and every panel; press it again and they come back as they were. Routing is Flow's: entering turns it on, with the mode this workspace last used in Flow or Balanced, and leaving turns it off, so the normal view picks the agent and model by hand and the **Agent** menu's choices wait until you leave. Handoff follows the mode rather than the Settings choice: Cost saving moves the task to another agent at 80% of a limit, Balanced at 90% and Maximum quality at 95%, without asking, and the Agents sheet shows no Handoff settings in Flow. In Flow the header spans the window: the seal and the word Flow sit beside the window controls with the workspace name, search is in the centre, and **Leave Flow** is at the far right. The space either side holds four cards that read what Codeshi has already recorded, with no model call: **How it’s working now** says in plain words how routing and handoff are set, where your next message would go, and has a **Review first** testing switch; **Agent settings** opens the routing controls; **What’s left on your plans** shows each connected agent’s tightest limit and when it resets; **What’s next** has the task plan and what’s queued; **Files changed** lists each run that changed files, with the same **Undo** as in the chat. Approvals, questions and Stop stay in the chat, and Flow has no bottom status bar. The working card shows live run status. **Your space** at the bottom left holds labeled **System**, **Dark** and **Light** choices and **Settings**; **Stay connected** at the bottom right holds **Remote access**, which opens a Flow sheet with the same pairing controls as Settings, and available update and keep-awake controls. **Terminal** and **Run** are unavailable in Flow, including their search, menu and keyboard entry points; leaving Flow restores the tools you had open. **Timeline** and **Review changes** stay available in **Files changed**, including before any files change. Going in, the seal appears for a moment while the layout changes. In a narrow window the cards become chips under the search bar, and a chip opens its card over the right edge. A separate **Your space** chip keeps preferences and phone access within reach. **Agent settings**, **Timeline** and **Review changes** open a Flow detail sheet with its own heading and no workbench tabs. **Back to Flow**, Escape or a click outside dismisses it and returns to the card; leaving Flow closes it and restores the earlier workbench layout. **All limits** opens Plan usage. Entering changes the view and uses the routing and handoff settings you already selected; it does not enable automatic handoff, change permissions or start tasks. Managed automatic task assignment and specialist teams remain planned.

**Changing views while work is active.** Entering and leaving Flow both wait until the workspace is idle, including other task threads, reviews, tests, automatic reset waits and unpaused queues. Finish or stop the work, cancel the wait, or pause the queue first; Codeshi never starts a new task just because you requested a view change. The button, keyboard command and desktop menu follow the same rule. **What’s next** links to task threads and waiting tasks, and **Workspace chat** returns from a task, so you can reach Stop, Cancel and queue controls without leaving Flow. Opening a waiting task shows its details without starting it; task-merge tests also hold view changes until they finish. A blocked attempt is not queued for later: choose the view again once the work ends. This guard is separate from the future per-task Flow execution policy.

The sidebar lists workspaces with search. A workspace with several folders shows them under its name; selecting a folder scopes its tasks and **Git activity** without opening Files. Tasks stay directly below the workspace list. The permanent conversation across every folder is named **Workspace chat**; its leading icon animates subtly while it works, unless reduced motion is enabled. Add, remove and rename are in **Workspace settings** (the ··· that appears when you hover a workspace). File previews and code blocks in replies are syntax colored.

**Optional Codex questions.** Codex can also ask a question while continuing to work. These show the same choices, a field for your own answer and **Skip**, and never choose an answer automatically. **Send answer** adds your reply to the current run. If the run has already finished, your reply is appended to the message draft instead; review it and use the normal **Send** control. Pending optional questions survive a restart and are superseded when you send a new prompt. This works on the phone too.

**Routing** belongs to Flow. Entering Flow turns it on with the mode this workspace last used or **Balanced**; leaving Flow returns to the agent and model you pick yourself. Choose **Cost saving**, **Balanced** or **Maximum quality** under **Routing** in the **Agents** sheet. The model button in the message box shows that mode and opens its settings.

**On Send, Codeshi rates the request, then chooses.** A short read-only agent assessment reads your prompt, the last few messages, the saved goal and plan, and attachment descriptions or short text excerpts. It evaluates difficulty and reasoning needs before Codeshi chooses the execution agent, model and supported effort level. A short follow-up can inherit the ongoing task's difficulty; an unrelated small request need not. The assessor does not perform the coding task or change your native coding session. It runs on a connected agent's smallest model with no tools, plugins or skills, typically in about three seconds, and its reported usage and working time count toward the same task's totals and limits.

A bare go-ahead such as "yes, do it" or "continue" carries on with the last rating, with no agent call, unless that rating was light: what it approves may be bigger than the light work before it. **Stop** cancels assessment, and changed workspace settings stop it too, with your draft preserved. If no agent can rate the request within about twelve seconds, or the answer can't be read, Codeshi uses a local estimate and sends the message anyway, never to a light model. Under each sent prompt, a note shows the final choice; hover over it for the reason and how the request was rated, including how long the agent took.

Codeshi checks every connected agent's account and plan usage on each Send. A slow check can't hold it up: after about two seconds Send goes on with that agent's last reading, and the check finishes for next time. It waits longer only for the agent keeping this conversation's session, or when no other agent can take the message. The chosen agent's billing and usage are verified again before it starts unless they were read moments earlier. Every applicable five-hour, daily, weekly and model-specific window constrains the choice; room in one cannot cancel exhaustion in another. Task difficulty sets the desired model and effort, with more headroom preferred for demanding work. Among suitable agents with usable allowance, the constraining window's reset time also influences selection, alongside remaining allowance and session continuity. An anticipated reset is never treated as available capacity: a passed reset needs a fresh reading. The router does not predict the exact tokens or duration of a task, and model tiers remain heuristics rather than measured quality rankings.

Assessment needs a connected agent with confirmed allowance and an enforceable read-only connection. Antigravity can execute assessed work when eligible, but is not used as the assessor because that connection cannot enforce read-only access. API-billed assessment and execution require explicit billing confirmation in addition to **Include API-billed agents**; unknown billing is not treated as free. An explicitly previewed **Build then review** workflow keeps its approved builder and model. Limits stay on the Flow cards rather than in the message box, since the agent isn't chosen until you send. Routed queued prompts and folder tasks are assessed when they start, with their access and permission settings preserved; handoffs reuse the original task assessment.

**Allowance and uncertainty.** Routing checks the model it would choose against every applicable five-hour, weekly and model-group window. A full weekly window still blocks that model when its five-hour window has room. Task limits on allowed models are applied before selection. Routing can try an equivalent-tier model, but does not downgrade only to escape a limit. Fresh known allowance is preferred to unknown usage; when all readings are unknown, the current eligible agent is preferred and the preview says **Plan usage unknown**. You can still send that manual request or choose a model yourself. A stale reading (over 15 minutes old or past a window's reset) is not treated as room; refresh usage to reconsider it. The preview's tooltip gives the observation time where known.

The backend refreshes usage for routed requests, including queued prompts, before starting the agent. If a relevant limit is now at 95% or more, or the reading is stale, it stops before launch and explains why. It never silently changes the chosen agent or model. Unknown usage stays explicit in the run's expandable details. Those details retain the windows and observation time across restarts. Readings are account-wide and include other clients; they do not reserve allowance or predict how many tokens or prompts will fit. Model tiers still use local name-based heuristics and are not verified capability or quality ratings.

**Testing cadence.** In **Settings › General › Testing**, choose **As needed** (the default) or **Review first**. As needed asks the agent to use checks appropriate to the change and avoid repeating successful checks without changed inputs. Review first keeps revisions ready for your review: broad suites, repeated builds and exhaustive end-to-end checks wait, while a syntax check or small regression check can still prevent a likely break or diagnose a failure. Ask “verify the changes” or explicitly request finalization, commit, push or release when you are ready; the agent is instructed to verify the relevant current changes before proceeding, reuse earlier results only when their relevant inputs are unchanged, and report anything still unverified. Merely changing the setting never starts a run or authorizes publication.

The setting applies to new turns across all workspaces, in Normal and Flow, including handoffs, resumed sessions and task threads. A running turn keeps its starting cadence. This is guidance to the agent, not a ban on test commands: explicit requests and mandatory repository checks still take priority. With Review first, Codeshi defers the routine **Check with tests** command and its automatic repair loop, with **Automatic tests deferred** shown in the conversation. Queued prompts can continue, but the deferral is not a passing test result; the status describes Codeshi’s command separately from checks the agent runs itself. An explicitly selected **Build, then review** workflow or test-repair retry retains its configured checks. Switch back to As needed to restore the routine loop. Flow’s working card shows the cadence and links to its setting.

**Check with tests.** Under **Routing**, **Check with tests** follows each routed run that changes files with this workspace's test command, the one marked **Use for Check with tests** in **Run**; it is never a command from the agent or the repository. The tests run as that command does when you start it, so you can watch them in **Run** and **Stop** them, and the result shows on the run's timeline with the end of the output. If the tests fail, routing tries once more one step up: the same agent, so it keeps its session, with a stronger model or more effort, told which command failed and the end of its output. **Balanced** and **Maximum quality** retry on their own with fresh confirmed allowance; **Cost saving** asks first, and so does any mode when that agent is near its limit (80% in Balanced, 90% in Maximum quality) has reached it, or its usage is unknown or stale. A retry is never retried: if the tests still fail, work stops there and you're notified. Queued prompts wait for the check and carry on once the tests pass; while they fail, the queue is paused. Tests that run for more than 10 minutes are stopped, and a test command that watches for changes never finishes, so mark one that exits. A run that changed no files, a model you chose yourself and a test command that is already running are not checked. The panel also shows how checked runs went, such as "Last 12 checked runs: 9 passed first time, 2 after a retry, 1 still failing."

Automatic handoff also needs fresh confirmed room on its destination, rechecked when an offer is accepted. If automatic fallback enters a reset wait, missing or stale readings cannot make it resume by themselves; the wait needs fresh confirmed room, or you can cancel it and choose manually.

Choose the agent, model, reasoning effort and access mode directly in the composer. Model and effort choices come from the installed provider's catalogue; custom model IDs remain available through **Enter a model ID…** (Gemini verifies a requested custom model ID against the ACP session before sending the prompt, while Antigravity exposes its native thinking-level choices and the advanced Gemini CLI connection leaves effort to its native model). Effort is remembered separately for each provider/model pair. The provider default remains an explicit choice. Reply headers show the model/effort recorded for that response when available; older replies are not given guessed model labels.

Each run reads as one thread under the agent's name, model and effort. A line runs down from the agent's icon, and what the agent says and each step it takes sit on it in order. What the agent says is the main text, with a dot in the agent's colour, so its explanations stand apart from its steps. A step is one compact row, such as **Run** `npm test` or **Read** `src/app.js`, coloured by its kind. A step that changes files lists them one per line, each file's name stronger than its folder, with the lines added and removed; new files are green and deleted ones red and struck through. A command step leaves off an outer shell wrapper where possible, and its chevron opens the exact command and output. Very long stretches keep their earlier steps behind one row. Steps allowed by full auto-approval are not listed again as approvals. The run's status line is the last step of its thread and its only live indicator: it says **Thinking**, **Working**, **Writing** or **Waiting for your approval**, with the elapsed time, and ends as **Completed in …** when the run finishes. Its chevron opens provider-reported token and context counts when available. After 30 seconds without provider events it says the agent is waiting, rather than claiming the model is thinking or stuck. Stop remains available. No private reasoning text or invented percentage is shown.

**Task plan** shows above the message box while the agent works: one line with how many steps are done and the current step. Click it to open the checklist, where done steps are ticked and the current one spins. The list stays open or closed as you left it while progress arrives, and starts closed for another run or workspace. The plan belongs to the task: it stays through a handoff, a wait for a reset or a stop, and when another agent continues, it says which agent it came from and that agent is told each step's status. A plan the new agent reports replaces it, and steps already done stay done unless that agent lists them again. A new prompt starts without a plan. The left panel remains workspace and file navigation, and the right panel holds optional details such as Git activity and review findings.

**Run** (in the status bar, or the bottom panel's **Run** tab) keeps the workspace's own commands: its dev server, tests, build, linter or any script. With none yet, it offers what the folder already defines, found by reading its files and never by running them: `package.json` scripts, `Makefile` targets, and the usual commands of Cargo, Go and Python projects. Click one to add it, or **Add command** to name your own, choosing the folder and subdirectory it runs in. A workspace keeps up to 12 commands. With several folders, the commands found are offered under each folder's name, the list on the left groups the commands under the folder each runs in, with **+** beside a folder to add one there, and a command in a subdirectory names it; the selected one's output starts with where it runs, such as **api** or **web/packages/ui**. The list shows each command's state (running, finished, failed or stopped); the selected one's output fills the rest, with its colours, and links to local addresses such as `localhost:5173` open in your browser. **Start**, **Stop** and **Restart** are beside it, the pencil edits or removes it, and **Clear** empties a finished command's output. When a command fails, **Ask an agent to fix it** puts the command and the end of its output in the message box, for you to read and send; nothing is sent by itself. Mark one command **Use for Check with tests** for routing's checks; a flask beside its name shows which. Commands run in your own shell with your permissions, whatever the agents' access, and keep running while the panel is hidden or another workspace is open; the status bar shows how many are running, or a red dot when one failed. Stopping a command stops everything it started, as do removing the workspace and quitting Codeshi. Commands saved before this version appear as **Run** and **Test**.

**Voice** (macOS). Press ⌥⌘V or click the microphone beside Send, speak, then press ⌥⌘V or the microphone again. While it listens, the status says **On this Mac**, because speech is recognized there and the audio never leaves it. What you say appears in the message box as it is heard, after anything you had already typed, for you to review and send; Esc cancels and leaves the message box as it was. Speech is recognized on your Mac by **Codeshi Speech**, a small helper that ships with the app, using Apple's on-device recognition: the audio never leaves your Mac. The first time, macOS asks to allow Codeshi Speech to use the microphone and speech recognition; you can change that later in System Settings › Privacy & Security. On-device recognition needs Dictation turned on for your language in System Settings › Keyboard. Listening stops on its own after two minutes. In **Settings › Voice**, **Send when I stop talking** sends what you said after a three-second countdown that Esc cancels. When a run you started by voice finishes, a short summary is read aloud with your system's voice: how long it took, the files it changed, whether it ran the tests, and the first sentences of the agent's reply. The summary is put together from what the run recorded, so it costs no agent usage. Choose whether summaries are read after voice runs, every run or never, and pick the voice. Ask about the project out loud too, such as "what did we decide about payments?"; the agent answers from the shared conversation and the answer is read back. On Windows, summaries can be read aloud; voice input is planned. Running from source builds the helper the first time you use voice input, which needs Xcode or its command line tools.

**While you were away.** Come back to Codeshi after two minutes or more and, if anything happened, a short recap opens under the search bar: for each workspace, the runs that finished, stopped or are still working, with what they were asked, how long they took, the files they changed and whether they ran the tests, then approvals and handoff offers waiting for you, waits for a usage limit to reset, queued prompts and uncommitted changes. Click a workspace to open it. **Read aloud** speaks the recap with your system's voice and highlights the row being read. The recap is put together from what Codeshi recorded, with no agent call. Open it at any time from the search bar (**While you were away**), and choose under **When you come back** in **Settings › Alerts** whether it opens on its own and whether it is read aloud.

**Point and tell** (desktop app). Show what should change instead of describing it. While an agent edits files in that workspace, the preview's toolbar shows its latest edit, as a file name and line counts, so you can watch a change land. While your dev server runs in **Run**, **Preview** beside its command opens its local address in a preview window (or choose **Preview your app** in the search bar). Click **Pick element** in the preview's toolbar: the element under the pointer is outlined and named, and clicking it picks it instead of pressing it; Esc stops. What you picked goes into the message box as a sentence, such as *In the preview of localhost:5173/checkout, the “Apply” button (form#promo > button.apply; src/PromoForm.tsx:42 in PromoForm):*, with a screenshot of the element attached. Say or type what should change after it and send it as usual; pick more to describe several at once, and **Go to message** in the toolbar brings Codeshi forward. The source file and line come from the app's development build where it reports them: React 18 and earlier, Vue and Svelte report them exactly, React 19 approximately, and inspector plugins mark them on the page; otherwise the agent finds the code from the text and the selector. The preview shows local addresses only: other links open in your browser, and it never opens windows, downloads files or grants permissions. Its cookies and storage are its own, so an app you sign in to there stays signed in there. The picker runs apart from the page's scripts, and the page never gets access to Codeshi or your files. When the agent changes the code, your dev server reloads the preview as usual.

**Terminal** (in the status bar, ⌃` or **View › Terminal**) opens your shell in the bottom panel, beside **Run**. A single-folder workspace opens its shell at once, and with several folders you click the one it starts in. Each shell is a tab in the list at the right of the terminal, named after its folder; hover over a tab to see the shell and the folder's path, and the arrow keys move between tabs. **+** at the top of the panel opens another shell in a tab of its own, in a folder you choose when the workspace has several (⌃⇧` opens one in the folder you're in). The split button puts a second shell, in the same folder, beside the one you're in, or under it with ⌥ held, so a dev server and a shell for commands can show side by side; each pane is its own shell, and a tab holds two. A workspace keeps up to eight shells. It is your login shell with your own environment, so commands, prompts, colours, interactive programs and copy and paste work as in any terminal, and keys typed there go to the shell, not to the message box. Click a link in its output to open it in your browser (in a web browser, in a new tab): an address a command prints, also when it wraps onto the next line, or a link a program marks up itself, which shows its address when you point at it. HTTPS links open, and HTTP links to this computer (`localhost`, `127.0.0.1` or `[::1]`), without a name or password in them; any other link says why it didn’t open. Agent access settings such as **Read only** don't apply to it. Hiding the panel, switching to **Run** or opening another workspace leaves the session and anything it runs, such as a dev server, running, and coming back shows it as you left it, including the latest output. The trash button ends the shell you're in and every process it started, closing its pane; the × on a tab ends all of that tab's shells. Removing the workspace and quitting Codeshi end them too. If a shell exits, a line under its output says how it ended, the output stays, and **New session** starts another in its place. Shells are kept while Codeshi runs; they can't be restored after it quits. Agents can edit files while a terminal runs; it takes no editing lock.

**Git activity** opens the repository inspector. For each attached folder it shows the current branch, staged/unstaged/untracked changes and the latest 15 local commits. GitHub origin repositories also get repository/commit links. It reads local history only and never fetches. The panel refreshes while visible; configured hooks, fsmonitor and external clean/process filters are disabled for its Git reads, so looking never runs code. A changed image (PNG, JPEG, GIF, WebP, BMP, ICO or AVIF) opens as pictures instead: the committed version and the one on disk side by side, or the one side an added or deleted image has, each with its size. Images over 4 MB, and files whose bytes are not the image their name says, are not shown.

**Committing.** In **Changes**, staged files are listed apart from the rest; hover a file and click **+** to stage it or **−** to unstage it, or use the buttons beside each list to stage or unstage everything in that folder. Write a message in the box above and choose **Commit** (⌘↵, or Ctrl+Enter), which names what the commit holds: with files staged it commits those, and with nothing staged it reads **Commit all**, stages every change listed and commits them. A commit holds exactly the files the panel shows: if anything else was staged meanwhile, by an agent or in a terminal, nothing is committed and the panel shows what is staged now; files staged outside the workspace folder must be unstaged or committed from their own folder. Commits use your own Git setup, as a commit from your terminal would: your name and email (shown beside the button), signing, filters such as Git LFS, and the project's commit hooks. If a hook stops the commit, its output appears under the box, and **Commit without hooks** commits with `--no-verify` only when you choose it. Codeshi never pushes; push from your terminal or ask an agent. Select a changed file to review its diff against the last commit (staged and unstaged together; new files in full). External diff drivers and textconv are disabled for diffs too. On wide windows the panel stays open unless you close it, and it refreshes when a run finishes.

Stage, unstage and commit wait for conflicting Codeshi work to finish: if an agent, patch, import, restore or task merge holds any folder in that repository, the action is refused without changing its index or HEAD. Try again after that work stops. This covers sibling folders even when you attached only one subfolder, and paths reached through links. Separate repositories and worktree indices remain available. While a commit hook runs, its repository stays leased and quitting waits for the action to settle; tasks waiting on that action retry after it finishes. These leases coordinate Codeshi's own operations; Git commands from a separate terminal use Git's own locks.

**Undo a run** (#20). Before an agent starts, Codeshi saves the workspace folders, and it saves them again when the run ends, whichever agent ran it. A run that changed files ends with a line such as **3 files changed · Undo** on its timeline. **Undo** first lists every file and what will happen to it: **Restore** (back to how it was before the run), **Remove** (the run added it), **Bring back** (the run deleted it) or **Merge** (the run's edits come out and later changes stay), each with the exact lines that change. Nothing is written until you confirm. A file changed since the run in the same places, deleted since, or a binary file changed since, is left as it is and listed, and so are links and nested repositories. If files change after you open the preview, Codeshi shows the updated preview instead of applying the old one. Undoing adds a note to the conversation, so the next agent knows those changes were taken back, and **Redo** puts them back. Undo is not available while an agent is working.

**Timeline and restore** (#20, stage 2). Open **Timeline** in the side panel, or search for **Timeline: review and restore checkpoints**. Runs are listed by agent and prompt, with **Before** and **After** checkpoints. Undos, redos and workspace restores appear too. Selecting a point opens a file preview; **Restore checkpoint** confirms it. This returns saved files to that point, replacing later edits and removing saved files added since. Unlike undoing just one run, it does not merge later edits. Files outside checkpoint coverage stay as they are and unsupported changes are listed. The conversation stays, with a note telling the next agent to inspect the restored files.

A restore saves **Before restore · recover** in Timeline before the first file write. Select that point and review its diff to return to the files from before restoring, including after an interrupted restore. Restore is unavailable while an agent works, when workspace folders changed, or when a selected checkpoint or current recovery snapshot cannot cover every attached folder. Shared workspace mutation locks also prevent restoring over another task. If files changed since the preview, review the updated preview before confirming again. Timeline currently belongs to the main workspace conversation; parallel task lanes use their existing task review and merge flow. Commits and optional conversation rewind remain planned.

Checkpoints are kept in Codeshi's data folder, never in your project's `.git`: your commits, branches, staged files and stash are not touched. Files your `.gitignore` leaves out, rebuilt folders such as `node_modules`, and files over 8 MB are not saved, and a folder with more than 60,000 files is not checkpointed. The newest 100 runs and 100 undo/restore operations in each workspace keep their checkpoints. Changes made while a run is working, by you or by a program such as a dev server, count as that run's changes; the preview shows them before anything is undone.

**Plan usage**, at the top of the **Agents** panel, lists your agents, and the one working now is marked **Working**, whichever is selected for your next message. With Ollama running and a model downloaded, **Ollama** is listed too, as local models with no limit; checking only reads what's installed. A connected agent shows its reported **5-hour** allowance as the main percentage and bar, with the limit's reset time underneath. The next most restrictive applicable limit, such as **Weekly** or **Weekly · Opus**, appears on a separate line with its own remaining percentage and reset time. Flow uses the same readings for the selected model. If no five-hour allowance is reported, the main reading uses the most restrictive reported limit and names its actual period. An agent that isn't connected shows its state, such as **Not installed**. Selecting a connected agent shows all its limits and reset times; selecting any other opens its setup in **Settings › Accounts**. The composer also leads with five-hour allowance for the selected agent and model, and adds a visible warning when another limit has 25% or less left. Selecting it shows all limits. Routing and handoff still check every applicable limit, so an exhausted weekly allowance blocks automatic selection even when the five-hour allowance has room. Codex usage comes from its app-server. Claude usage comes from an experimental Claude Agent SDK call and is shown as unavailable if a future SDK removes it. The pinned Antigravity connection reads its built-in `/usage` account report without an LLM turn. Bucket names, remaining allowance and reset times come from Google; unavailable quota, absolute counts and disabled limits are never converted into estimated percentages. Per-run context tokens are separate from account allowance. The advanced Gemini CLI connection does not report account quota through this integration. Reading usage never starts inference.

**Continue when a limit resets.** When a run stops on a usage limit, choose **Continue when a limit resets** to let the task wait instead of you. Codeshi reads each connected agent's plan usage, shows when each limit resets, and continues the unfinished task on whichever agent has room first, from the shared conversation, as it does when you switch by hand. An agent that reports no reset time is checked again every ten minutes; reading usage does not use your allowance. The continued run uses the access and permission setting shown on the wait and is never given more: with **Ask before changes** it pauses at the first change that needs approval, and if full auto-approval is on you choose whether it applies while you are away. A wait survives restarting the app, ends after a day, and is replaced by any message you send yourself. If the continued run reaches another limit, it waits again, up to three times. **Cancel** stops waiting.

**Tasks side by side.** With a folder selected, **+** beside **Tasks** in the sidebar opens a blank task in that folder, using the usual message box, so you can choose any agent, model and access. Before you send it, it says how it would run, what else is running and what it will already know, and it starts when you send it. It's listed under **Tasks** with its own output, approvals, queue and **Stop**, and a badge says when one needs you. In a workspace with several folders, selecting the workspace lists all its tasks and the Workspace chat, and selecting a folder lists that folder's tasks and shows its files. In a workspace with one folder, you see both. A prompt waiting under **Up next** can start now instead: **Run as a task** on its row moves it out of the queue and starts it beside the current run, with the agent, model and access it was queued with. How it runs is one of these:
- **Directly in the folder**, when nothing else is using that folder or its repository.
- **In its own copy**, a Git worktree from the last commit, when something is using the repository, even under another folder's name. It doesn't include uncommitted changes, and the blank task says how many that leaves out. **Review and merge** then shows each file against the folder as it is now, and can run your test command on the combined result in a temporary copy. Changes on both sides are merged when they don't touch. A conflict stops the whole merge and overwrites nothing, and **Keep as a branch** gives you the task's work to merge by hand.
- **Waiting its turn**, outside Git, where a copy isn't possible. It starts by itself when the folder is free.

**Start after** holds a task until another finishes, or is merged if it worked in a copy. **Tasks at once** in the task limits covers these and the Workspace chat together, 2 by default. An agent with full auto-approval that has no sandbox of its own, which is any but Codex, could reach other folders, so it doesn't run directly beside other work. After a restart, a task that was running shows as stopped and one that was waiting asks you to start it. If a task's folder leaves the workspace, its history stays and it can't run.

**Queue prompts.** While an agent is working or the task is waiting for a reset, **Queue** (or Enter) adds your message to **Up next** instead of sending it. Queued prompts run one after another, each with the agent, model, effort, access and permission setting shown on it when it was queued, never more. Reorder, edit or remove them until they start. If a queued run reaches a usage limit, the task waits for a reset and the queue carries on afterwards. At a handoff, prompts queued for the agent that ran out move to the agent that took over, keeping their access and permission setting and taking that agent's model and effort; a routed prompt is routed again. **Up next** says which prompts moved. If Codeshi stops while a prompt is being sent, that prompt is never sent again by itself, and the conversation says so. Any other stop pauses the queue, as does restarting Codeshi, and **Resume queue** continues it. A workspace can queue up to 20 prompts.

**Add to the run.** To add a point or correct something while the agent is working, type it and choose **Add to run** (⌘↵, or Ctrl+Enter on Windows and Linux) instead of **Queue**. The agent takes your note into the task it is already doing, without stopping the run or starting over: Codex and Claude read it at their next step, and Gemini continues the same session with it. The note appears inside that run, marked **Added while working**. If the run finishes before your note reaches the agent, it goes first in the queue and runs next with the same settings. Attachments go with queued messages only.

**The agent's plan.** When an agent breaks the task into steps, the plan appears as one line above the message box, showing how many steps are done and what the agent is doing now; open it for the full to-do list. The list is the agent's own plan, from Codex's plan and Claude's to-do list, and from Gemini when its connection reports one (Antigravity keeps its plan to itself for now). It updates as the agent works. Agents plan longer tasks on their own; short tasks may not have a plan.

**Handoff.** In Flow, a routed run hands off by its routing mode (see Flow above); the settings here apply to the normal view. While a cloud agent works, Codeshi checks its plan usage after the first few seconds and then about once a minute. Once it passes 90% of a limit, an offer appears under the run: it names the agent it would hand off to, that agent's model and billing, the access and permission setting it would use (the same as the current run, never more) and the task it would continue. **Hand off** stops the run and the other agent continues the task from the shared conversation; **Not now** keeps the run going and is not asked again during that run. The offer also says how many queued prompts would move. Accepting covers exactly those, so a prompt that changes after you accept stays where it was, and if the destination bills per use, its charges for those prompts are a separate choice. When a task that crossed agents finishes, one line gives its total working time, without any wait for a reset, the files each agent changed and the latest test result. Only connected agents below the threshold are offered, subscription-billed ones first. An agent billed to an API account, or whose billing cannot be confirmed, needs its charges accepted separately before **Hand off** is available. An offer is checked again just before switching: if the task, the workspace folders, the saved project context or the other agent's model, access or billing changed, nothing is started on the other agent and an updated offer replaces it. Choose when offers appear, or turn them off, in **Settings › General › While agents work**, under **Handoff** in the **Agents** panel, or **Agent › Hand Off Near Usage Limits** in the desktop menu. These are the same app-wide preferences. **Hand off automatically** switches without asking, only to subscription-billed agents with room, and says so in the conversation and a notification. It's off until you turn it on.

A run can still reach its limit: usage can jump between checks, or you may have said **Not now**. With **Hand off automatically** on, the task then continues on an agent with room, with the same access and permission setting, and the conversation names both agents and when the limit resets. A weekly or model-specific limit counts as no room, even when the agent's 5-hour window is free. If no agent has room, the task waits for the first reset as **Continue when a limit resets** does, and you can cancel the wait. With it off, the run stops and you choose what happens; the first time, **Always do this** beside **Continue with…** turns it on. Queued prompts carry on after a handoff.

**Tasks.** The **Tasks** panel shows the current task, with the agents involved, working time, new tokens and whether the tests passed, and lists the tasks before it with the agents involved, working time, tokens as each agent reported them, and whether the project's tests passed. A task follows its handoffs, retries and reviews, and time spent waiting for a limit to reset isn't counted. A value an agent didn't report shows as not reported, never as zero, and "At least" marks a run that was stopped before its final count. Tokens aren't turned into a price, and plan usage stays separate because other tools count toward it. All of this comes from the saved conversation on your computer. **Export without prompts** saves a copy with no prompts or commands.

**Memory.** **Remember** on a message or step keeps it for every agent in this workspace, or you can add one under **Memory** in the **Brief** panel. Select part of a message first to keep only that part. An entry is a convention, a decision, a working fix or a failed approach, for one folder or all of them. Codeshi also suggests things you wrote as lasting rules, such as "Decision: …" or "Remember that …", and approaches that failed in a task whose tests later passed. It works these out locally with no model, and nothing is kept until you choose **Keep**.

Agents are told conventions and decisions for the folders in scope, and fixes and failed approaches when the task mentions what they're about, within about 4 KB. A resumed session only hears what's new. If a file an entry names has changed, the entry is sent marked for a recheck rather than as fact, and shows **Needs recheck** in the list. Your requests always take priority over memory. Memory stays in Codeshi's own data, out of your repository and out of conversation exports and Ask a Friend, and each workspace has its own. **Retire** stops an entry being used, and a retired one can be restored or deleted. Deleting removes the entry from memory, while the conversation it came from stays saved.

**Skills.** A skill is a procedure in the [Agent Skills](https://agentskills.io/specification) format: a folder with a `SKILL.md`. **Skills** in the **Brief** panel lists what's enabled; **Add skills** finds six optional starters, your repository's skills (in `.agents/skills`, `.claude/skills`, `.codex/skills` or `.gemini/skills`) and any folder you add. Nothing is on until you enable it, including a repository's own. To use one, type `/name` in a prompt, or say "use the name skill". A skill that clearly matches a task is used by itself, at most one per message, and each step says **Using skill** and why. Agents get only the names and descriptions of the others, and can read one if a task needs it. A skill in use goes with the task to the next agent.

Enabling a skill keeps a private copy, so it stays at that version until you choose **See update** and **Use this version**, or never if you **Pin** it. Your own files aren't touched, and **Remove** only drops the copy. Skills reach every agent as instructions in the prompt, so what relies on one agent's own skill system is listed as unavailable, such as hooks or placeholders, and enabling one of those takes an explicit choice. Codeshi never runs a skill's scripts; an agent may, with its own tools and under your approvals. A skill can't change your access, approvals or billing, or override your requests or the repository's instructions. **Make a skill** on a memory turns it into one after you've reviewed it, and the skill records where it came from.

**Task limits.** The sliders button in the **Tasks** panel sets one budget for a whole task, across its agents, retries and reviews. A new prompt starts a new task. You can limit working minutes, new tokens (input, output and cache writes, not cached reads), API spend, and how many handoffs, retries and reviews it may use, and choose which agents the workspace may use. Time, tokens and spend have no limit until you set one. Every run is checked before it starts, so nothing goes around a limit, and handoff never offers a move a limit would refuse.

Background reviews share the parent task's time, token and API-spend totals while they work. Reported usage is saved in the main conversation journal, so a restart retains the latest sample even if the reviewer never produced a final report. Reviews also take a slot in the workspace's **Tasks at once** limit, alongside the main conversation and folder tasks. If you set a time, token or spend limit, its remaining allowance is reserved for one worker on that task: wait for its current agent to finish before continuing or reviewing the same task. Other tasks keep their own budgets. Limits cannot be newly applied or changed while multiple agents are working on the same task; finish one first.

Reaching a limit stops the run, saves its work and says why. Carrying on with that task is then refused until you choose **Allow more**, which applies to that task only. Tokens are only counted as agents report them, so in-flight work can overshoot, and what it reported is shown. An agent that reports nothing can't be held to a token limit, and the panel says when a total is missing runs. API spend counts only runs confirmed as billed per use. The native Claude connection receives the remaining spend cap, including for a background review; other connections are checked as costs are reported. Run details distinguish native enforcement from reported-usage checks. An agent that reports no cost can't be held to a spend limit, and unknown billing is never counted as a known API charge. These checks have been tested with simulated providers, not a real paid API run. The same failure repeated, by default 5 times, also stops a run. That count belongs to the task, so restarts and changing agents don't reset it, and the next agent is told what has already failed.

Usage limits are judged one by one: room in the 5-hour window doesn't make up for a full weekly one. An agent whose usage is unknown or out of date can still be offered as a handoff, and the offer says so.

**What a new agent is told.** An agent that starts fresh, such as after a handoff, gets the current task first. Alongside it come the folders it concerns, each folder's instruction files (`AGENTS.md`, `CLAUDE.md`, `GEMINI.md`), the files changed so far with a hash of each as it is now, what already went wrong and the steps left. This is worked out on your computer without a model. A task narrows to the folders it names; if it names none, it stays with the last task's folders, or keeps them all. Work from other folders and repeated steps are left out, and the agent is told so and can find the originals in the saved conversation. A session that resumes only hears what changed. Everything except your own requests and the repository's instructions is marked as evidence to check, so text from a file or a command can't pass as an instruction. Credentials and private folders are never included. The **Brief** panel shows what the next agent would get right now, and **See the full brief** opens all of it; a note you add there goes with it.

**Alerts.** When you are in another app, Codeshi can tell you about three moments: an agent **needs you** (an approval, a question or a handoff offer), a task **finished**, or a task **stopped** (an error, a usage limit or failing tests). **Settings › Alerts** lists each way it can tell you as a row you turn on or off, with a box for each moment, so you can, for example, hear a sound only when an agent needs you. A way you turn off keeps its choices for when you turn it back on.

- **Banner**: a system notification, or the panel near the top of the screen described below. Clicking it opens its workspace, and one for an approval opens that exact request without answering it. macOS does not allow notifications for builds without a Developer ID signature, so until signed builds ship (#1), choose the panel if banners don't appear. On Windows, notifications use the Start menu shortcut Codeshi keeps up to date for this.
- **Sound**: a short sound for each moment, which Codeshi plays itself, in the desktop app and in a browser, so it works without notification permission; banners stay silent so you never hear two. **Play** lets you hear each one first. Set the volume, and choose **Play sounds only when Codeshi isn’t in front** to keep it quiet while you are looking at it. Sounds are off until you turn them on, and a run you stop yourself plays nothing.
- **Bounce the Dock icon**: once, or until you open Codeshi when an agent needs you. On Windows, the taskbar button flashes instead.
- **Badge on the Dock icon**: how many things happened since you last looked.

**Agent › Alerts** turns each way on or off from the menu bar, and **Alert Settings…** there opens the section. While Codeshi is in front it shows what happened itself, so banners and the Dock stay quiet, and coming back to it closes the panel. Progress reports, such as a task continuing after a usage limit resets, show like a finished or stopped task but play no sound. Alerts name the workspace and agent but never show commands, chat text or file paths. In the sidebar, a workspace with requests waiting shows how many, even while another workspace is open.

**Status in the menu bar** (macOS). Codeshi's mark, シ, in the menu bar shows what your workspaces are doing while you work in other apps. Beside it, a few words say what needs you, such as **Approval needed** or **Tests failed**, or what the one working agent is doing, such as **Codex · Editing · 3 files changed**, or how many are working; with nothing running, only シ shows, with a dot in its corner when something needs you. Click it for a list of busy workspaces, the ones that need you first: approvals, failed tests, retries and handoffs to answer, then work in progress, waits for a usage limit and paused queues. Choosing one opens that workspace, and an approval opens its request card; nothing is answered from the menu. **Keep Awake** there shows and changes the same setting as the status bar. Its **Alerts** menu turns each way of alerting you on or off, as **Agent › Alerts** does. Like notifications, the status never shows commands, chat text or file paths, only general words and counts. Hide it with **Hide from Menu Bar**, or turn it off with **Show what agents are doing in the menu bar** in **Settings › Alerts** or **Status in the Menu Bar** under **Agent › Alerts**.

**The panel near the top of the screen** (macOS, off by default). Choose **Panel at the top of the screen** as the banner style in **Settings › Alerts**, and banners appear in a small panel under the menu bar of the screen you're working on, in place of notifications, so nothing is announced twice. It never takes the keyboard from the app you're using and doesn't appear over full-screen apps. A dot on its シ shows what happened: amber when an agent needs you, green when one finished and red when one stopped. Click it to open the workspace or the request; **×** dismisses it. An approval stays until it is answered or dismissed, or until you come back to Codeshi; anything else goes after eight seconds. With banners turned off, it stays quiet too.

**Keep awake** in the status bar (desktop app) stops your computer and its display from sleeping while any workspace has an agent running or is waiting for a limit to reset, so a long run is not interrupted. It shows **Auto** while switched on and waiting, **On** while it is holding the computer awake, and releases as soon as the last run finishes. The setting is remembered between launches and is also available in **Settings › General**.

The appearance buttons in the status bar choose **System**, **Dark** or **Light**, and **Settings › General** and setup offer the same choice. **System**, the default, follows your computer's light or dark setting as it changes; **Dark** and **Light** stay as chosen. Both use the logo's colours: **Dark** is warm black with cream text, **Light** is cream paper with dark ink, and vermilion, the red of the seal, marks the main action and what is selected. In the desktop app, native menus and dialogs use the same appearance.

Messages and code blocks have copy buttons.

The bug form starts with your Codeshi and macOS versions filled in.

## Cross-agent review

After a completed task, **Review changes…** (shown under the run when there are changes, and always in the search bar and the **File** menu) suggests the eligible changed files and prepares their exact diff preview. The goal is filled from the current task. Adjust the selected files if needed, inspect the preview and choose **Start read-only review**. Unknown or API billing needs explicit confirmation before the review can consume usage. The toolbar's **Review** action also supports choosing files manually.

The reviewer runs in a separate worker against copies of the approved files and their diffs. Its results appear in a side panel while you send your next prompt in the Workspace chat. Only selected files are copied; unrelated project files and native agent sessions are not transferred into this snapshot. The review cannot edit the live workspace, and stopping it does not stop the main agent. Close the panel and reopen it from **View review** at any time.

Later edits to selected files, Git state or attached folders make the report outdated. Select findings to prepare a fix draft only after the review completes and freshness checks pass. The fix request is added after whatever is already in the message box, whose text and attachments stay, for you to edit and send; a fix draft never starts an agent automatically. Failed, interrupted and unstructured reviews show that status instead of claiming there were no issues. App shutdown stops background workers, and interrupted reviews can be restarted. Finish or stop a background review before changing folder membership or removing the workspace.

**Build, then review.** Write a coding prompt, choose **Review after** in the composer, and select the repository folders to review. The dialog shows the builder, the reviewer and its saved model, and explains the additional run against your own account. Claude builds are reviewed by Codex; Codex and Gemini builds are reviewed by Claude. API or unverified billing requires its own confirmation. Choose **Review after this prompt**, then **Send**. The authorization applies to that exact prompt, attachments, saved brief, model choices and folder membership. Changing any of those asks you to confirm again. Local runs, queued prompts and Continue use manual review instead.

The authorized scope is all reviewable uncommitted text changes in the selected repository roots when the builder finishes, including changes that were already there. Private files, binary files and symbolic links are excluded. The usual limits apply: 12 files, a 72 KB snapshot and 1 MB per current file. If the scope cannot be captured completely within those limits, the sequence stops and you can choose files for a manual review. The captured filenames and exact diffs remain available under **Reviewed scope**.

The builder must finish successfully. If **Check with tests** is configured, those checks must pass too; failures pause this sequence instead of automatically retrying the builder. Adding a note to the running task or changing its saved brief cancels the automatic review authorization. A usage limit may still offer a handoff, but changing builders requires your explicit choice for this run.

The run shows its build and review phases, with **View review** opening the results and **Stop review** ending only the reviewer. You can send another task while it reviews the saved copy; later edits can make its findings outdated. Queued prompts stay on hold and pause for your decision when the sequence ends. There is at most one automatic review per prompt: select findings to prepare an editable fix request and press **Send** yourself. Interrupted builds, failed reviews and app restarts stop the sequence; nothing resumes or repeats automatically.

## Files and attachments

Click **Files** beside the Workspaces heading to open a separate file browser, or choose **View → Show Files** in the desktop menu. At the workspace level it shows each folder as a separate root; after selecting a folder it shows just that folder. Expand directories and select a file: the browser closes and its read-only text/code or image preview opens, with **Attach to message** available. Close the preview to return to your conversation. Escape closes the file browser. Opening and closing Files does not resize the sidebar or move Tasks. The browser hides private app data, credentials, provider sessions, dependency folders and symbolic links. Large directories load in pages.

Click **Attach** in the composer, drag files onto it, or paste an image from your clipboard. Click an attachment chip to preview it, or its × to remove it before sending. Supported inputs:

- PNG, JPEG, GIF and WebP images, up to 5 MiB each.
- UTF-8 text and code (including Markdown, JSON, CSV and source files), up to 64 KiB each.
- Up to six files and 20 MiB per message, with a combined text limit of 128 KiB. The prompt context budget still applies.

PDF, Office, audio, video and other binary attachments are not supported. SVG is treated as text, never rendered as active content. Images require the native Codex app-server, Claude SDK or an ACP-capable Gemini CLI reporting image prompt support; the optional plain CLI adapter rejects image input explicitly.

Files are saved as immutable snapshots in the workspace’s local application storage. Selecting or previewing a file starts no inference; **Send** transmits it to the selected agent. Draft attachments stay with their workspace and survive reloads and failed sends. Journals store attachment metadata, not image base64. Recent unseen text/image attachments are included on model handoff within context/image limits; the agent is told when older images are omitted.

The first launch opens a short setup: a welcome, then three steps (connect your agents, choose the theme and default access, and choose your project folders) and a summary before the app appears. **Finish** leads to the summary, and **Open Codeshi** completes setup. Previous conversations are offered inside the workspace after setup. **Skip for now** leaves a **Getting started** shortcut in the sidebar, and **Settings › Setup guide** reopens the steps at any time. Setup never changes existing chats.

Updates and reinstalls open your saved workspaces directly. After an update, a dismissible **What’s New** panel shows release notes bundled with the installed app, including recent releases you skipped. Once dismissed, it does not reopen automatically for that version. **Help › What’s New** reopens it at any time, including offline. The first update from a version without version tracking shows the installed version's notes without guessing the previous version. Downgrades and reinstalling the same version do not announce another update.

**Updating.** The macOS app checks GitHub Releases shortly after it opens and every six hours. When a newer version is out, an **Update to** button with the version appears in the status bar. One click downloads the zip for your Mac (Apple Silicon or Intel), checks it against the release's published SHA256 checksum and checks the app inside (its version, bundle ID and signature), while a ring on the button fills; click the button while it downloads to **Cancel**. Nothing is installed if any check fails. Once the update is ready, the button becomes **Restart to update**: one click quits, replaces the app and opens the new version with your workspaces as they were. Restarting never stops an agent: while one is working, or a queued prompt is about to start, the button says **Restarts after this run** and Codeshi restarts once no agent is working; **Don’t restart** in its details keeps the update ready. If you quit instead of restarting, the update is put in place as Codeshi closes and opens next time. The chevron beside the button has the release notes and **Skip this version**, which hides the offer until a newer release; **Codeshi › Check for Updates…** shows it again. On Windows, run the PowerShell installer again to update. Turn automatic checks off, or check now, under **Updates** in **Settings › General**. A copy opened straight from Downloads runs from a temporary location macOS creates, and a copy in a folder you can't write to can't replace itself; both offer the download instead, so move Codeshi to Applications to update in place. A check asks GitHub for the public release list and sends nothing about you or your projects.

## Import Claude Code and Codex chats

Create or open a workspace first. Codeshi checks its project folders for previous Claude Code and Codex conversations and offers **Review conversations** when it finds chats that have not been merged. The suggestion never opens a dialog or merges messages by itself. **Not now** is remembered for that workspace across restarts; after a successful merge, the automatic suggestion is also dismissed.

Choose **Previous chats** from the search bar (⌘K) or the **File** menu. The list defaults to **This workspace**, matches folder paths, and groups chats by project folder. Select one or several conversations from either agent, review their messages together, and confirm **Merge conversations**. Nothing is selected automatically. Messages merge into the open workspace’s single conversation by their original times, with their source and timestamps preserved.

**Browse other projects** is a secondary option for explicitly choosing unrelated chats. Their existing folders are attached to the open workspace if needed, with those additions shown before merging. Folders that no longer exist are reported and not attached. **Open conversation file…** brings a shared conversation into the workspace you have already opened. The destination workspace is always shown in the review.

Importing copies visible user and assistant text, original timestamps and available model provenance. Claude Code slash-command records, native tool state and hidden reasoning are not imported. Import never resumes a native session, starts inference or modifies the provider's original conversation. When you next press **Send**, the selected agent starts with the imported history as shared context (most recent messages first, within the context budget) and runs on your own installed CLI and account. Codeshi supplies no API keys of its own.

Discovery and preview use the installed Claude Agent SDK session readers and the Codex app-server history APIs; both read local history. Codeshi's own runs are excluded from the list. Each import confirms that the reviewed content has not changed; a changed source must be previewed again. Repeated imports are deduplicated, and a reviewed import of a grown conversation updates its partial messages. Each conversation is limited to its most recent 1,000 text messages and 2 MiB, with clipping disclosed, and up to 20 conversations can be imported at once.

## Export a conversation

**Export conversation**, from the search bar (⌘K) or the **File** menu, saves the conversation as a `.codeshi.json` file that another Codeshi user can open with **Previous chats › Open conversation file…** after opening their own project workspace; files exported as `.throughline.json` before the rename open too. They review the messages and continue with their own Claude, Codex or Gemini account. Nothing runs during export or import.

By default an export contains the user and assistant text of the whole conversation plus the saved goal, decisions and tasks. Secrets and local paths are removed, and workspace paths become folder names such as `[frontend]/src/app.js`. You can limit it to recent messages, include tool activity, or turn removal off; the dialog shows what the file contains before you save it. **Save as Markdown** writes a readable copy instead. A file holds up to 2 MB of conversation (the oldest messages are left out first). A file that was edited after export is rejected on import. On import, shared context fills only fields the receiving conversation has not set, and the other person's messages are shown as theirs. Import files only from people you trust, because their messages become context for your assistant. To ask someone for code changes and receive a reviewable patch instead, use **Ask a Friend**.

## Ask a Friend

The default view prepares a local preview from the current task and up to eight recent conversation messages. No form is required: edit the filled-in request if you wish, optionally include the suggested changed source files, then inspect the exact preview. **Export request file** approves and exports that preview. **Create private link** approves and publishes that preview only when a sharing service is configured. Opening the view never approves or publishes anything. Changes to the request require a refreshed preview. Source files are opt-in, and secret scanning can miss private information.

**Advanced request editor** retains exact message selection, source paths, decisions, tasks and editable package JSON. The complete workflow is:

1. In the original conversation click **Ask a Friend**. Enter the problem and expected outcome; select individual messages or tool logs.
2. Choose **Context only** or **Selected source**. Enter only approved workspace-relative text-file paths. Add specific permitted new-file paths if a returned patch may create files. The repository is never selected automatically.
3. In multi-folder workspaces use the displayed folder prefix, such as `frontend/src/app.js`, to distinguish files. Prepare the offline preview. Inspect and edit the actual outgoing JSON, inventory and warnings. Refresh an edited preview to recalculate its integrity. Confirm and approve that exact content.
4. Export the approved JSON offline, or configure a separate sharing service under **Solutions & links** and create a private link.
5. Your friend can view/download the approved material and submit a solution in a normal browser. They use their own tools and account; the website cannot access their local subscriptions. Codeshi is optional for them.
6. If they use Codeshi, **Help a friend** imports into a deliberately selected local workspace and its existing chat; map each shared folder to an attached local folder. Importing writes no source files and starts no assistant. They can prepare files locally, then build/export an exact solution against the approved baseline. Upload that solution through the friend webpage, or return the JSON offline.
7. Retrieve or import solutions under **Solutions & links**. Explanations and contributor verification appear in the original conversation. Review each diff before choosing **Apply reviewed patch**. Instructions-only solutions have no automatically applicable code.
8. Run an explicitly reviewed local syntax/whitespace check. Recovery restores affected baseline files when safe and preserves unrelated or newer edits.

A private link grants its holders view and submission access until expiry or revocation. The owner capability remains in local private storage. Default expiry is seven days; the service supports bounded expiry and revocation. Creation/delivery needs connectivity; preparation, approval, export/import, diff, application, recovery and supported verification do not need AI or internet. Lost upload responses retry with the same persisted upload identity. One rejected patch does not prevent receiving other valid solutions.

Source baselines retain exact approved content and SHA-256 hashes, including dirty and selected untracked files. Git commit identity alone is insufficient. Patches support explicit UTF-8 text-file create/replace/delete operations for approved paths, up to 128 files and 256 KiB per file, within the 2 MiB portable-package limit. Unsafe paths, private runtime paths, symlinks, binary content and unapproved baselines are rejected. Changed target files become conflicts and are not overwritten. The app never resets, stashes or commits a user's project. Request and solution IDs make delivery/application idempotent. Previews bind to a private workspace snapshot; changing workspace folders requires preparing a new preview. Approved requests and recovery checkpoints keep their original folder mapping and refuse writes to detached roots. Durable recovery checkpoints precede file writes.

Verification is intentionally limited to reviewed `node --check relative-file.js` and `git diff --check`. Imported commands and arbitrary package scripts never run automatically. Git external diffs, text converters, hooks and configured clean/process filters are disabled for this whitespace check. Broader tests can be run deliberately in your own terminal.

Default exclusions cover environment/credential files, provider session stores, runtime data and unnecessary absolute paths. Transcript redaction and secret scans assist review; they cannot guarantee that sensitive content has been removed. Review source and conversation text yourself before approving.

## Private-link service

For a same-computer test:

```sh
npm run sharing
```

Set the GUI service URL to `http://127.0.0.1:4319`. These are local test links; another computer cannot open them. Remote links require a separately deployed HTTPS service with persistent private storage. Each release publishes a container image, `ghcr.io/ahmednavaz/throughline-sharing`; it keeps its name from before Codeshi was renamed. Deployment, Docker, limits, capabilities and proxy configuration are in [sharing/README.md](../sharing/README.md), and [sharing/deploy](../sharing/deploy) has ready-made templates for Docker Compose with Caddy, which gets the HTTPS certificate by itself, and for Fly.io. `AI_RELAY_SHARING_URL` can configure the client, and `AI_RELAY_SHARING_CREATE_KEY` can provide the service's optional creation key.

The sharing service stores only approved packages and solutions. It has no execution endpoints, provider credentials, repository mounts or account integration. Do not expose or tunnel the local coding server. Production hosting has **not** been deployed or verified by this implementation.

## Saved data and migration

Desktop data lives under Electron's OS application-data directory in `Codeshi/relay-data` (on macOS, `~/Library/Application Support/Codeshi/relay-data`; on Windows, `%APPDATA%\Codeshi\relay-data`). Codeshi was called Throughline: an installation from before the rename keeps using its `Throughline` folder, or `AI Relay` from before that, so nothing moves. Projects, append-only journals, local collaboration associations, owner capabilities and recovery files stay there. Treat this directory as private. Source folders do not need Codeshi files.

The first development launch copies the old checkout's `.data` into OS storage if no desktop data exists. The original remains untouched, and `migration.json` records the source. Migration refuses live legacy locks, invalid locks or unfinished guards. Stop all old Codeshi instances first. To import from a different checkout on first launch:

```sh
AI_RELAY_LEGACY_DATA_DIR=/absolute/old/AI-Relay/.data npm start
```

For an existing installation, perform that one-time development launch before moving to the packaged build. Packaged apps deliberately exclude `.data`; they use the same OS storage. Migration never merges over an existing destination. For rollback, quit all instances and retain both copies; reopen the original checkout with its original `.data`. Restoring old data does not undo later file edits. Workspace mutation locks also exclude overlapping folders across different history roots on the same user account. A surviving provider process after a crash blocks conflicting edits until it has stopped; guards with a known dead owner recover automatically. Empty guards left by older versions and unrecognized guard content still fail closed with recovery instructions; stop all instances before inspecting those guards.

For a browser-only development session use `npm run web`, optionally with `-- --workspace /absolute/project --port 4318`. This uses checkout `.data` by default. Set `AI_RELAY_DATA_DIR` explicitly if you want it to use another history store. The execution server binds to loopback, checks Host/Origin and mutation headers; desktop additionally uses a per-launch token and isolated renderer with narrow folder/external-link IPC.

## Running from source

Build a standalone app for your OS and architecture with `npm run package`; the result is written to `dist/`. The logo is drawn in code in `desktop/brand.mjs`. After changing it, run `npm run icons` on a Mac to rewrite every icon from it: the layered macOS 26 icon and its compiled `assets/Assets.car`, the `.icns` used by earlier macOS versions, the Windows `.ico`, the menu bar images, the favicons and the brand PNGs in `assets/brand/`. Compiling the layered icon needs Xcode 26 or later.

Electron starts and stops the loopback backend itself. No separate server terminal is required. Close the app to stop its managed provider processes. A second desktop launch focuses the existing window. Run from source (`npm start`), the app is **Codeshi Dev**: a separate app with its own data folder (`~/Library/Application Support/Codeshi Dev`) and its own window, labelled **Dev**, so it runs alongside an installed release without sharing workspaces, conversations or settings. Without a signing identity, `npm run package` signs macOS builds ad hoc; they are not notarized.

The development launcher clears an inherited `ELECTRON_RUN_AS_NODE` flag before opening Electron, so `npm start` also works from terminals hosted by an Electron-based editor or coding agent. Provider workers run in Node mode themselves but clear the flag before starting an agent, so an Electron app an agent starts, such as Codeshi from source, opens normally.

To replay onboarding from the welcome screen, run `npm run start:fresh` or `npm start -- --fresh`. Each launch uses an empty temporary profile and skips legacy-data migration. Setup changes and imported chats in that session are discarded when the window closes; existing saved workspaces stay intact. Installed agent sign-ins are still detected. To preview a new user with no agents installed, run `npm run start:fresh -- --no-agents`; this hides the agents only for that temporary session and leaves their installations and sign-ins unchanged.

If package installation disabled lifecycle scripts, run `node node_modules/electron/install.js` once to install Electron's official runtime. Build a fresh app for the current OS/architecture with `npm run package`; output goes to `dist/`. `AI_RELAY_SIGN_IDENTITY` can supply an installed macOS signing identity. Notarization requires separate Apple credentials/configuration.

## Limitations

- macOS builds are signed ad hoc and not notarized, so macOS asks you to approve a browser download once. Windows builds are not signed, so SmartScreen asks you to confirm a browser download once (**More info**, then **Run anyway**). Linux builds are not provided yet.
- The private-link sharing service is not hosted for you. Run the container image yourself with HTTPS and persistent storage, for example with one of the templates in `sharing/deploy` (see `sharing/README.md`), before sharing remote links.
- Returned patches support UTF-8 text files only; binary files and symlinks are rejected, and stale baselines need a new solution.
- Built-in verification covers reviewed JavaScript syntax and `git diff --check`, not arbitrary test scripts.
- Secret scanning and redaction help you review what you share; they cannot guarantee that every secret is removed.
- Claude's and Gemini's restricted tools are not an operating-system sandbox. Hidden reasoning and native process state do not move between providers.
- Claude plan usage comes from an experimental Claude Agent SDK call and may stop being reported after an SDK update. Antigravity quota requires native Google sign-in for this connection. The advanced Gemini CLI connection does not expose account quota here.
